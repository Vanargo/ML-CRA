# Инструкция выполнения выпуска ML-CRA 1.0.0 через GitHub

## Статус и граница полномочий

Этот документ является проверяемой инструкцией, а не разрешением на выпуск.
Он может исполняться только в отдельно авторизованном John блоке ST08_16C
`ST08_16C_v1_0_0_GitHub_execution`; будущая авторизация должна охватывать узкую
финализацию release-state — состояния выпуска — и GitHub Release `v1.0.0`, но
не TestPyPI, PyPI, изменение научных артефактов или замену уже опубликованных
тегов/активов.
До успешного `assurance` точного SHA и отдельного подтверждения John на слияние
защищённого PR необратимая часть авторизации не исполняется.

## Почему требуется переход состояния

Текущие `README.md`, `README_RU.md`, `RELEASE_NOTES_1.0.0.md` и `CITATION.cff`
правдиво описывают локальный неопубликованный кандидат. Публикация этого дерева
без перехода сделает утверждения «не опубликован» ложными и повторит известный
дефект формулировки v0.1.0. Поэтому текущие локальные активы являются
воспроизводимым preflight — предварительным — кандидатом, но не готовыми к
немедленной загрузке release-активами.

## Обязательные предварительные условия необратимого шага ST08_16C

1. John принял ST08_16B и отдельным явным решением подтвердил стабильность
   ограниченного публичного API версии 1.0.0.
2. John отдельно передал `NEXT_BLOCK_AUTHORIZED` для ST08_16C вместе с узкой
   финализацией четырёх release-state поверхностей.
3. `README.md` и `README_RU.md` больше не называют v1.0.0 неопубликованным
   локальным кандидатом и точно описывают канал GitHub Release без заявления
   публикации в PyPI.
4. `RELEASE_NOTES_1.0.0.md` переведён из candidate-снимка в финальные
   двуязычные notes — примечания — без изменения научного scope — границы.
5. Если в `CITATION.cff` добавляется `date-released`, она должна быть реальной
   датой выполнения выпуска; выдуманная или будущая дата запрещена. Поле
   необязательно и не должно добавляться, если точная дата ещё неизвестна.
6. Все изменения зафиксированы в отдельном commit — фиксации — и прошли pull
   request с обязательным `assurance` именно для точного SHA; John отдельно
   подтвердил слияние, а exact release commit находится в `main`.
7. Из точного проверенного Git index дважды построены и зарегистрированы
   `ml_cra-1.0.0.tar.gz`, `ml_cra-1.0.0-py3-none-any.whl` и `SHA256SUMS`.
8. Тег и GitHub Release `v1.0.0` отсутствуют; `v0.1.0` и `v0.1.1` остаются
   неизменяемыми.
9. Ruleset `main`, secret scanning, push protection, Dependabot alerts,
   private vulnerability reporting и Release immutability подтверждены.

Если хотя бы одно условие не подтверждено, выполнение останавливается без
создания тега или draft — черновика.

## Последовательность ST08_16C

Порядок существенен:

1. Финализировать четыре release-state поверхности в разрешённых границах.
2. Зафиксировать переход, открыть PR и дождаться успешного `assurance` точного
   commit; после отдельного решения John объединить PR в `main` и проверить
   post-merge `assurance`.
3. Повторно построить из exact main commit два совпадающих комплекта трёх
   активов.
4. Убедиться в отсутствии `v1.0.0` и повторно проверить репозиторные меры.
5. Создать draft GitHub Release для нового тега `v1.0.0`, направленного на
   точный проверенный commit; не публиковать draft на этом шаге.
6. До публикации прикрепить все три актива.
7. Сверить имена, размеры и SHA-256 дистрибутивов со строками `SHA256SUMS`.
8. Один раз опубликовать draft при включённой неизменяемости выпусков.
9. После публикации выполнить:

   ```powershell
   gh release verify v1.0.0 --repo Vanargo/ML-CRA
   gh release verify-asset v1.0.0 .\dist\st08_16C-release\ml_cra-1.0.0.tar.gz --repo Vanargo/ML-CRA
   gh release verify-asset v1.0.0 .\dist\st08_16C-release\ml_cra-1.0.0-py3-none-any.whl --repo Vanargo/ML-CRA
   gh release verify-asset v1.0.0 .\dist\st08_16C-release\SHA256SUMS --repo Vanargo/ML-CRA
   ```

10. Зарегистрировать URL, release ID, тег, точный commit/tree, дату, имена,
    размеры, SHA-256, результаты четырёх команд и release attestation —
    удостоверение происхождения выпуска.

## Остановка и восстановление

- До публикации ошибочный draft не публикуется; его исправление, удаление или
  пересоздание выполняется только в явно разрешённых границах ST08_16C.
- После публикации тег и активы неизменяемы. Нельзя молча заменять их для
  исправления текста или байтов.
- TestPyPI и PyPI не входят в ST08_16C и остаются отдельным решением John.
- SHA-256 подтверждает совпадение байтов, но не доказывает корректность,
  научную состоятельность или отсутствие неизвестных уязвимостей.
