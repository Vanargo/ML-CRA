# Протокол следующего диагностического контура OpenML-кандидатов

Документ сопровождает `REPORT_28` и задает рамку для следующего этапа работы.

## 1. Общий принцип

Первый диагностический запуск подтвердил, что технический контур загрузки данных, отбора признаков, разбиения, обучения и сохранения результатов работает. Следующий контур должен не увеличивать сложность моделей, а проверить устойчивость постановки.

## 2. `openml_electricity_151`

Обязательное дополнение: временное разбиение.

Правило: обучать модели на ранней части последовательности, проверять на поздней части последовательности. Поля `date`, `day`, `period` должны использоваться только для восстановления порядка или диагностики порядка, но не как модельные признаки первого контура.

## 3. `openml_miniboone_41150`

Обязательное дополнение: повторные стратифицированные случайные разбиения.

Правило: использовать несколько заранее зафиксированных зерен случайности. Для каждой модели сохранять не только одно значение метрики, но и среднее, минимум, максимум и стандартное отклонение.

## 4. `openml_click_prediction_small_41434`

Обязательное дополнение, если кандидат остается в проекте: абляция идентификаторов.

Правило: безопасный контур без идентификаторов остается основным. Контур с идентификаторами разрешен только как демонстрация риска и должен быть явно помечен как `leakage_risk_diagnostic`, то есть диагностический запуск с риском утечки данных.

## 5. Запрещено на следующем этапе

1. Менять статусы кандидатов до выполнения второго диагностического контура.
2. Подбирать гиперпараметры.
3. Использовать рискованный контур с идентификаторами как финальную оценку качества.
4. Интерпретировать один случайный запуск как устойчивый результат.
