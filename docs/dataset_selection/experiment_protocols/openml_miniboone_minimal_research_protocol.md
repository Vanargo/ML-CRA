# Протокол: минимальная исследовательская оценка `openml_miniboone_41150`

Дата: 2026-05-07  
Статус: проектный протокол до кодовой реализации  
Кандидат: `openml_miniboone_41150`  
Рабочая роль по `REPORT_31`: `primary_tabular_candidate`

## 1. Цель отчета

Цель `REPORT_32` — зафиксировать минимальный воспроизводимый исследовательский протокол для основного табличного кандидата `openml_miniboone_41150` до написания следующего кода.

Этот отчет не запускает модели, не меняет код, не меняет тетради и не меняет `dataset_candidate_registry.csv`.

## 2. Входные внутренние основания

В `dataset_candidate_registry.csv` после `REPORT_31` кандидат имеет статус `primary_tabular_candidate`. В той же строке зафиксировано, что повышение основано на повторном стратифицированном диагностическом контуре: `hist_gradient_boosting mean ROC AUC=0.983444, ROC AUC std=0.000595, PR AUC=0.955148 across 5 seeds`.

По файлу `data_registry/openml_second_diagnostic_summary.csv` для `openml_miniboone_41150` получены следующие диагностические значения:

- `hist_gradient_boosting`: `roc_auc_mean=0.983444`, `roc_auc_std=0.000595`, `pr_auc_mean=0.955148`, `f1_mean=0.895585`, `balanced_accuracy_mean=0.928877`;
- `logistic_regression`: `roc_auc_mean=0.938743`, `roc_auc_std=0.001082`, `pr_auc_mean=0.866641`, `f1_mean=0.776090`, `balanced_accuracy_mean=0.833514`;
- `dummy_prior`: `roc_auc_mean=0.500000`, `pr_auc_mean=0.280629`, `f1_mean=0.000000`.

Эти значения остаются диагностическими: поле `row_status` равно `diagnostic_draft`, а поле `interpretation_allowed` равно `no`.

## 3. Решение `REPORT_32`

Решение: не расширять эксперимент сразу на новые модели и подбор гиперпараметров. Сначала нужно провести минимальную воспроизводимую внешнюю оценку на уже проверенной связке:

1. `dummy_prior` — базовый контрольный классификатор;
2. `logistic_regression` — линейная модель с `StandardScaler` (стандартизатор признаков) внутри `Pipeline` (конвейера обработки);
3. `hist_gradient_boosting` — нелинейная древовидная модель без обязательного масштабирования признаков.

Основное разбиение для `REPORT_33`: `RepeatedStratifiedKFold` (повторная стратифицированная k-блочная проверка) с `n_splits=5`, `n_repeats=2`, `random_state=20260507`.

Причина выбора: второй диагностический контур уже показал устойчивость на 5 зернах случайности. Следующий минимальный шаг должен дать распределение качества по 10 внешним проверочным блокам, а не один случайный тест.

## 4. Запрещенные действия на этапе `REPORT_33`

На этапе `REPORT_33` запрещено:

1. Подбирать гиперпараметры на тех же внешних блоках, где считается качество.
2. Использовать тестовые блоки для выбора модели.
3. Менять список признаков `ParticleID_0 ... ParticleID_49`.
4. Подгонять `StandardScaler` (стандартизатор признаков) до разбиения.
5. Повышать статус кандидата выше `primary_tabular_candidate`.
6. Делать вывод о финальном качестве ML-CRA по одному набору данных.

Если на следующем этапе потребуется подбор гиперпараметров, нужен отдельный протокол вложенной проверки: внешняя проверка для оценки качества, внутренняя проверка для выбора параметров.

## 5. Минимальный исследовательский контур

### 5.1. Данные

- Источник: OpenML, набор `MiniBooNE`, идентификатор `41150`.
- Целевая переменная: `signal`.
- Положительный класс в диагностике: `True`.
- Признаки: `ParticleID_0` ... `ParticleID_49`.
- Разрешенный тип признаков: числовые признаки.
- Обработка пропусков: при обнаружении пропусков выполнение должно быть остановлено до утверждения отдельного протокола.

### 5.2. Разбиение

Основной контур: `RepeatedStratifiedKFold` (повторная стратифицированная k-блочная проверка), `n_splits=5`, `n_repeats=2`, `random_state=20260507`.

Для каждой пары «модель — блок проверки» должны сохраняться:

- номер повтора;
- номер блока;
- размер обучающей части;
- размер проверочной части;
- доля положительного класса в обучающей части;
- доля положительного класса в проверочной части.

### 5.3. Модели

Разрешены только три модели:

- `dummy_prior`;
- `logistic_regression`;
- `hist_gradient_boosting`.

Все параметры должны быть явно записаны в выходной таблице. Подбор гиперпараметров запрещен.

### 5.4. Метрики

Основные метрики:

- `roc_auc` — площадь под ROC-кривой;
- `pr_auc` — площадь под кривой точность-полнота;
- `f1` — F-мера;
- `balanced_accuracy` — сбалансированная точность;
- `log_loss` — логарифмическая потеря;
- `brier_score` — оценка Брайера.

Для каждой метрики нужно сохранить среднее, стандартное отклонение, минимум, максимум и количество внешних проверочных блоков.

## 7. Критика решения

Слабое место 1: выбранный протокол пока не использует вложенную проверку. Это допустимо только потому, что в `REPORT_33` запрещен подбор гиперпараметров.

Слабое место 2: протокол опирается на OpenML-метаданные и внутренний реестр, но вопрос первичной публикации, происхождения и цитирования MiniBooNE еще не закрыт. Перед использованием в статье или диссертации требуется отдельная проверка первоисточника и правил цитирования.

Слабое место 3: `hist_gradient_boosting` уже показывает очень высокое качество. Это может быть нормальным свойством данных, но может также скрывать особенности набора или процедуры. Поэтому нужны сохранение индексов блоков, контроль распределения классов и отдельная проверка отсутствия технической утечки.

Слабое место 4: один основной кандидат не доказывает общность ML-CRA. Он подходит для первого стабильного табличного контура, но не заменяет будущие временные, категориальные и рискованные контуры.
