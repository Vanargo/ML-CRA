# Протокол предобработки признаков OpenML-кандидатов

## 1. Статус

Этот протокол относится к трем кандидатам:

```text
openml_electricity_151
openml_miniboone_41150
openml_click_prediction_small_41434
```

Протокол не запускает обучение моделей и не создает кодовые файлы. Он фиксирует правила будущей предобработки признаков до перехода к `.ipynb` и `.py`.

## 2. Главный принцип

Любое преобразование признаков должно выполняться только внутри будущего обучающего контура после разбиения данных. Запрещено подгонять масштабирование, кодирование категорий, заполнение пропусков, отбор признаков или целевое кодирование на полном наборе данных до разбиения.

Проектное основание: `REPORT_24_openml_minimal_model_protocol.md`, раздел `5. Что нельзя делать`, строки 87–95: «Нельзя: 1. обучать модели до утверждения протокола предобработки; ... 4. подгонять преобразования на полном наборе данных до разбиения; 5. выбирать победителя до определения разбиений, метрик и предобработки.»

Методологическое основание: официальная документация scikit-learn по типичным ошибкам и конвейерам обработки указывает, что данные нужно сначала делить на обучающую и тестовую части, не вызывать `fit` (подгонку) на тестовой части, а `Pipeline` (конвейер обработки) помогает избежать утечки данных.

## 3. Общая политика по типам признаков

| Тип признаков | Решение первого контура |
|---|---|
| Числовые обычные признаки | Использовать. Для логистической регрессии — стандартизировать внутри будущего конвейера обработки. Для древовидных моделей — не масштабировать без необходимости. |
| Категориальные признаки с малой кардинальностью | Допускать только после явного перечисления и только через кодировщик внутри будущего конвейера обработки. |
| Временные поля | В первую очередь использовать для восстановления временного порядка и временного разбиения. Как обычные предикторы — только отдельным диагностическим режимом. |
| Идентификаторные признаки | В основной безопасной постановке исключать. Использовать только в отдельной чувствительной проверке после утверждения дополнительной политики. |
| Пропуски | По текущему локальному просмотру пропусков нет. Если в будущей загрузке они появятся, эксперимент нужно остановить и обновить протокол, а не молча заполнять пропуски. |
| Целевое кодирование | Не входит в первый минимальный контур. |

## 4. `openml_electricity_151`

### 4.1 Подтвержденная структура

В локальном просмотре зафиксированы 45 312 строк, 8 признаков, целевая переменная `class`, отсутствие пропусков и временные признаки-кандидаты `date`, `day`, `period`. Проектное основание: `data_registry/openml_data_preview_summary.csv`, строка 2.

Признаки по локальному просмотру:

```text
date; day; period; nswprice; nswdemand; vicprice; vicdemand; transfer
```

Проектное основание: `data_registry/openml_feature_preview.csv`, строки 2–9.

### 4.2 Основная политика первого контура

Обычные числовые предикторы первого контура:

```text
nswprice; nswdemand; vicprice; vicdemand; transfer
```

Для `LogisticRegression` эти признаки должны стандартизироваться внутри будущего конвейера обработки. Для `HistGradientBoostingClassifier` и условного `RandomForestClassifier` масштабирование не требуется как обязательное решение первого контура.

### 4.3 Временные поля

Поля `date`, `day`, `period` в первом основном контуре используются как поля восстановления временного порядка и проверки временного разбиения, а не как обычные предикторы. Это консервативное решение, потому что архив фиксирует их как временные признаки-кандидаты, но не фиксирует окончательное правило включения их в модельные признаки.

Отдельный будущий режим можно назвать:

```text
electricity_include_time_features_diagnostic
```

Он допустим только после отдельного решения, где будет явно указано, какие временные поля доступны в момент предсказания и не создают искусственного усиления утверждения.

## 5. `openml_miniboone_41150`

### 5.1 Подтвержденная структура

В локальном просмотре зафиксированы 130 064 строки, 50 признаков, целевая переменная `signal`, отсутствие пропусков и только числовые признаки. Проектное основание: `data_registry/openml_data_preview_summary.csv`, строка 3.

Признаки `ParticleID_0` ... `ParticleID_49` указаны как числовые. Проектное основание: `data_registry/openml_feature_preview.csv`, строки 10–59.

### 5.2 Основная политика первого контура

Все 50 числовых признаков используются в первом контуре.

Для `LogisticRegression` используется стандартизация внутри будущего конвейера обработки. Для `HistGradientBoostingClassifier` и условного `RandomForestClassifier` масштабирование не требуется как обязательное решение первого контура.

Отдельная осторожность: набор крупнее остальных; архив уже фиксирует вычислительную нагрузку как риск для условного случайного леса. Проектное основание: `data_registry/openml_dataset_model_matrix.csv`, строки 7–9.

## 6. `openml_click_prediction_small_41434`

### 6.1 Подтвержденная структура

В локальном просмотре зафиксированы 39 948 строк, 11 признаков, целевая переменная `click`, отсутствие пропусков, классы `0=33220; 1=6728`, а также идентификаторные признаки-кандидаты. Проектное основание: `data_registry/openml_data_preview_summary.csv`, строка 4.

Идентификаторные признаки-кандидаты:

```text
url_hash; ad_id; advertiser_id; query_id; keyword_id; title_id; description_id; user_id
```

Проектное основание: `docs/dataset_selection/identifier_protocols/click_prediction_identifier_policy.md`, раздел `2. Идентификаторные признаки`, строки 13–27.

### 6.2 Основная безопасная политика

В основной первой постановке все идентификаторные признаки исключаются. Проектное основание: `docs/dataset_selection/identifier_protocols/click_prediction_identifier_policy.md`, раздел `4.1 Безопасная базовая политика`, строки 38–48: «Исключить все идентификаторные признаки. Это основная безопасная политика для первой версии.»

Остающиеся безопасные неидентификаторные признаки первого контура:

```text
impression; depth; position
```

Проектное основание: `data_registry/openml_feature_preview.csv`, строки 60, 64, 65.

Для `LogisticRegression` эти признаки стандартизируются внутри будущего конвейера обработки. Для `HistGradientBoostingClassifier` масштабирование не требуется. Условный `RandomForestClassifier` не должен запускаться до оценки нагрузки и размера представления признаков.

### 6.3 Запрещенные и отложенные политики

Запрещено кодировать идентификаторы как обычные признаки без сравнения с безопасной политикой. Проектное основание: `docs/dataset_selection/identifier_protocols/click_prediction_identifier_policy.md`, раздел `5. Запрещенные политики`, строки 68–76.

Целевое кодирование не входит в первый минимальный контур. Проектное основание: `docs/dataset_selection/identifier_protocols/click_prediction_identifier_policy.md`, раздел `4.3 Отложенная политика`, строки 62–67.

## 7. Контрольные правила перед будущим кодом

Перед написанием `.ipynb` или `.py` нужно сохранить этот протокол и CSV-план. Затем будущая тетрадь должна проверять:

1. совпадает ли фактический список признаков с ожидаемым;
2. отсутствуют ли пропуски;
3. не попали ли идентификаторы `Click_prediction_small` в основную безопасную постановку;
4. не используются ли временные поля `electricity` как обычные предикторы без отдельного диагностического режима;
5. выполняются ли масштабирование и кодирование только внутри будущего конвейера обработки;
6. не запускается ли обучение моделей до утверждения следующего технического шага.

## 8. Решение

Отчет 25 должен создать два не кодовых артефакта:

```text
data_registry/openml_feature_preprocessing_plan.csv
docs/dataset_selection/preprocessing_protocols/openml_feature_preprocessing_protocol.md
```

После переноса этих файлов следующим логичным шагом будет план тетради первого безопасного эксперимента, но сама тетрадь должна создаваться только после подтверждения, что протокол предобработки перенесен и принят.
