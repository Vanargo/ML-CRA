# Этап 3 — диагностические эксперименты

## 1. Назначение документа

Этот документ фиксирует диагностическую часть проекта: первые технические запуски, проверку жизнеспособности кандидатов, проверку чувствительности к разбиению и предварительное распределение ролей.

## 2. Статус этапа

Статус: завершен для трех OpenML-кандидатов после `REPORT_31`. Новые диагностические запуски добавляются сюда только если появляется новый кандидат или требуется восстановить ошибку.

## 3. Цель диагностики

Первый диагностический контур должен был подготовить данные и протоколы к будущим минимальным экспериментам, но еще не обучать модели; также он должен был получить техническую проверку жизнеспособности кандидатов. Текущая архивная копия источника: `docs/archive/reports/REPORT_21_openml_first_diagnostic_contour_plan.md`, страница: не применяется, раздел `1. Цель диагностического контура`, строки 15–27. Дословный фрагмент: «Цель первого диагностического контура — подготовить данные и протоколы к будущим минимальным экспериментам, но еще не обучать модели ... получить техническую проверку жизнеспособности кандидатов».

Диагностика включала уровни проверки постановки задачи, допустимых способов разбиения, риска утечки данных и выбора метрик. Текущая архивная копия источника: `docs/archive/reports/REPORT_21_openml_first_diagnostic_contour_plan.md`, страница: не применяется, раздел `3. Уровни диагностики`, строки 47–96. Дословный фрагмент: «Уровень 1 — проверка постановки задачи ... Уровень 2 — проверка допустимых способов разбиения ... Уровень 3 — проверка риска утечки данных ... Уровень 4 — выбор метрик».

## 4. Минимальный набор моделей

Первый диагностический этап не должен был начинаться со сложных моделей; требовался минимальный, воспроизводимый и интерпретируемый набор. Текущая архивная копия источника: `docs/archive/reports/REPORT_24_openml_minimal_model_protocol.md`, страница: не применяется, раздел `1. Главный принцип`, строки 17–27. Дословный фрагмент: «На первом диагностическом этапе нельзя сразу использовать сильные и сложные модели ... Нужен минимальный, воспроизводимый и интерпретируемый набор моделей».

В первый диагностический контур включались `DummyClassifier`, `LogisticRegression`, `HistGradientBoostingClassifier`. Текущая архивная копия источника: `docs/archive/reports/REPORT_24_openml_minimal_model_protocol.md`, страница: не применяется, раздел `3. Решение по моделям`, строки 44–54. Дословный фрагмент: «В первый диагностический контур включаются три модели: DummyClassifier; LogisticRegression; HistGradientBoostingClassifier».

## 5. Признаки и предобработка

Первый контур использовал только признаки, обоснованные архивом и не требующие рискованных преобразований. Текущая архивная копия источника: `docs/archive/reports/REPORT_25_openml_feature_preprocessing_protocol.md`, страница: не применяется, раздел `3. Главное решение`, строки 47–56. Дословный фрагмент: «Главное решение: первый контур должен использовать только такие признаки, которые уже обоснованы материалом архива и не требуют рискованных преобразований».

## 6. Итоговая диагностическая развилка

По итогам двух диагностических контуров роли распределены так: MiniBooNE — основной табличный кандидат, electricity — временной кандидат, Click_prediction_small — удержанный пример риска идентификаторов. Текущая архивная копия источника: `docs/archive/reports/REPORT_31_openml_candidate_status_update.md`, страница: не применяется, раздел `6. Итоговое решение`, строки 107–115. Дословный фрагмент: «Принять рабочее обновление реестра: openml_miniboone_41150 — primary_tabular_candidate; openml_electricity_151 — temporal_sensitivity_candidate; openml_click_prediction_small_41434 — leakage_risk_diagnostic_hold».

Важно: это не финальный выбор набора данных и не финальное утверждение качества моделей. В `REPORT_31` прямо зафиксированы слабые места: MiniBooNE еще не проверен на внешние сдвиги распределения и финальную лицензионно-метаданную пригодность; решения основаны на диагностических контурах. Текущая архивная копия источника: `docs/archive/reports/REPORT_31_openml_candidate_status_update.md`, страница: не применяется, раздел `5. Самокритика решения`, строки 97–105. Дословный фрагмент: «MiniBooNE проверен на устойчивость к зернам случайности, но пока не проверен на внешние сдвиги распределения и не прошел финальную проверку метаданных и лицензии ... все три решения основаны на диагностических контурах, а не на финальном исследовательском протоколе».

Этап завершен, если:

1. диагностические файлы сохранены;
2. роли кандидатов перенесены в реестр;
3. текущим основным кандидатом назначен MiniBooNE;
4. ограничения этапа зафиксированы;
5. следующий этап работает уже не с тремя кандидатами, а с основным кандидатом и протоколом надежности оценки.
