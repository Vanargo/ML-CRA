# ML Claim Reliability Auditor (ML-CRA)

[English version](README.md)

<!-- ST08-10:status -->
## Статус и границы

ML-CRA проверяет, поддерживают ли экспериментальные доказательства
**ограниченное** утверждение машинного обучения. Инструмент не выбирает
универсально лучшую модель и не превращает результат одного набора данных в
общую рекомендацию.

Этот публичный репозиторий является снимком разработки версии `0.1.0.dev0`. Это
не авторизованный релиз. Наблюдения публикации репозитория, размещённой
непрерывной интеграции (hosted CI) и репозиторных мер безопасности ограничены
[записью доказательств ST08_13B](data_registry/st08_13B_public_repository_hosted_CI_and_security_evidence_v01.json).
Поддерживаемые пользовательские сценарии — локальная бинарная табличная
классификация и ограниченная табличная регрессия с обменными строками на
Windows x64 с CPython 3.12, а также формирование локальной статической панели на
русском и английском языках из проверенного пакета доказательств.
Многоклассовая классификация, временная или групповая регрессия, произвольный
импорт моделей, входы pickle/joblib, URL, автоматический подбор
гиперпараметров, интерактивная или размещённая панель и размещённый сервис не
поддерживаются.

Английская и русская инструкции описывают одинаковые команды. Пользовательская
диагностика CLI сейчас выводится по-русски; локализация диагностики пока не
является поддерживаемой функцией.

<!-- ST08-10:purpose -->
## Что делает инструмент

`mlcra audit` проверяет отдельное для типа задачи версионированное
JSON-утверждение и локальный UTF-8 CSV, сравнивает две фиксированные разрешённые
реализации на зарегистрированных парных разбиениях и записывает пакет из восьми
файлов. Бинарная классификация использует стратифицированные разбиения, а
регрессия — K-fold только при заявленном допущении `exchangeable_rows`
(обменные строки). `mlcra verify`
без обучения моделей проверяет точный состав пакета, хеши, связи происхождения и
вердикт. `mlcra doctor` сообщает, соответствует ли установленное окружение
заявленной ячейке, и перечисляет незакрытые релизные шлюзы.

Успешный аудит может вернуть `supported`, `fragile` или `not_supported`. Все три
категории являются корректными ограниченными результатами, а не программными
ошибками. См. [контракт продукта Stage 8](configs/project_readiness/stage08_public_product_scope_and_release_train_contract_v01.json)
[JSON Schema бинарного утверждения](src/mlcra/schemas/binary_classification_claim_v01.schema.json)
и [JSON Schema регрессионного утверждения](src/mlcra/schemas/tabular_regression_claim_v01.schema.json).

## Предварительные условия

- Windows x64;
- CPython `>=3.12,<3.13`;
- локальная копия исходного репозитория;
- доступ к настроенному индексу пакетов Python во время приведённых ниже команд
  установки. Поддерживаемые операции `audit`, `verify` и `doctor` сеть не
  используют.

Локально наблюдалась ячейка CPython 3.12.0 / Windows Server 2019 AMD64. Ячейка
GitHub Actions с CPython 3.12.10 на `windows-2022` настроена; её наблюдённый
результат фиксируется, а не выводится из одной конфигурации, в записи ST08_13B.
Подтверждённая поддержка Linux, macOS, ARM64, PyPy и других версий Python не
заявляется.

## Воспроизводимая установка из исходников

Выполните команды из корня репозитория в PowerShell. Первые две установки
используют точные версии и SHA-256. Затем проект использует уже установленный
фиксированный backend сборки и не разрешает новые зависимости.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --require-hashes --only-binary=:all: -r requirements/locks/st08_09-assurance-tools-py312-windows-x86_64.txt
.\.venv\Scripts\python.exe -m pip install --require-hashes --only-binary=:all: -r requirements/locks/st08_07-py312-windows-x86_64.txt
.\.venv\Scripts\python.exe -m pip install --no-build-isolation --no-deps .
.\.venv\Scripts\mlcra.exe doctor --format json
```

Ожидаемый результат: `doctor` завершается с кодом `0` и возвращает
`"environment_pass": true`. Значение `"release_ready": false` сохраняется
намеренно: повторный аудит кандидата на релиз от 24 августа 2026 года дал
`FAIL` для проектной завершённости и `FAIL` для готовности к внешнему релизу.
Остаются незакрытыми полный накопительный pilot, исторические контрольные точки,
проспективный повторный аудит кандидата на релиз v02 и решение John о выпуске.
Публичная инфраструктура разработки сама по себе не является релизом.

## Быстрый старт

Следующий сценарий для локальной копии использует небольшой синтетический
пример. Он не изменяет зарегистрированные доказательства MiniBooNE и не
использует сеть. Новый пакет записывается в каталог с уникальным именем внутри
системного временного каталога.

```powershell
$ClassRunDir = Join-Path ([System.IO.Path]::GetTempPath()) ("mlcra-classification-demo-" + [guid]::NewGuid().ToString("N"))
$RegressionRunDir = Join-Path ([System.IO.Path]::GetTempPath()) ("mlcra-regression-demo-" + [guid]::NewGuid().ToString("N"))
$DashboardDir = Join-Path ([System.IO.Path]::GetTempPath()) ("mlcra-dashboard-demo-" + [guid]::NewGuid().ToString("N"))
.\.venv\Scripts\mlcra.exe audit --spec tests/fixtures/st08_08/binary_claim_v01.json --data tests/fixtures/st08_08/binary_data_v01.csv --output-dir $ClassRunDir --format json
.\.venv\Scripts\mlcra.exe verify --bundle $ClassRunDir --format json
.\.venv\Scripts\mlcra.exe audit --spec tests/fixtures/st08_11/regression_claim_v01.json --data tests/fixtures/st08_11/regression_data_v01.csv --output-dir $RegressionRunDir --format json
.\.venv\Scripts\mlcra.exe verify --bundle $RegressionRunDir --format json
.\.venv\Scripts\mlcra.exe dashboard --bundle $RegressionRunDir --output-dir $DashboardDir --format json
```

Ожидаемый результат каждого `audit`: код `0`, ограниченный вердикт `supported`
для синтетического примера и ровно следующие файлы в его каталоге вывода:

`run_manifest.json`, `input_validation.json`, `environment.json`,
`provenance.json`, `audit_summary.json`, `verdict.json`, `warnings.json` и
`artifact_index.json`.

Ожидаемый результат `verify`: код `0`, `"status": "PASS"`,
`"verified_artifacts": 8` и `"model_fit_performed": false`. После просмотра
временные пакеты можно удалить. Эти синтетические результаты проверяют работу
программы, но не являются зарегистрированными научными выводами на реальном
наборе данных.
Команда панели сначала проверяет bundle, затем записывает
`dashboard_view.json`, `dashboard_en.html`, `dashboard_ru.html` и
`dashboard_manifest.json`. Обучение и сеть не используются; обе HTML-страницы
являются точными представлениями одного проверенного JSON.

## Граница входных данных

Утверждение должно проходить поставляемую схему своего типа задачи. Любой CSV
должен содержать заголовок, одну явно указанную цель и хотя бы один полный
конечный числовой признак. Для бинарной классификации дополнительно нужны ровно
две метки и достаточное число строк каждого класса. Для регрессии нужны полная
конечная числовая непостоянная цель, как минимум вдвое больше строк, чем
разбиений, и явное допущение `exchangeable_rows` (обменные строки). Программа не
может проверить это допущение по одному CSV: временные, групповые, повторные или
пространственно зависимые наблюдения требуют отдельного зарегистрированного
протокола разбиения.

Для классификации разрешены `hist_gradient_boosting_v01` и
`logistic_regression_v01` с `average_precision`. Для регрессии разрешены
`hist_gradient_boosting_regressor_v01` и `ridge_regression_v01` с
`root_mean_squared_error`; положительная разность означает RMSE базовой модели
минус RMSE кандидата. Модели и гиперпараметры фиксируются до выполнения.
Требуется новый каталог вывода; перезапись отклоняется.

<!-- ST08-10:exit-codes -->
## Коды завершения

| Код | Значение |
|---:|---|
| `0` | Выполнение по контракту завершено, включая любую корректную категорию вердикта |
| `2` | Ошибка использования командной строки |
| `3` | Ошибка контракта входа или спецификации |
| `4` | Доказательств недостаточно для корректного вердикта |
| `5` | Контролируемая ошибка окружения или выполнения модели |
| `6` | Нарушение внутреннего инварианта или целостности пакета |

Ошибки обрабатываются с закрытием при неопределённости: неуспешная операция не
публикует успешный пакет, а обычный пользовательский режим не выводит
неперехваченную трассировку стека.

<!-- ST08-10:troubleshooting -->
## Устранение неполадок

- `environment_pass=false`: используйте CPython 3.12 на Windows x64, точно
  установите оба lock-файла и повторно установите проект с
  `--no-build-isolation`.
- `MLCRA_OUTPUT_ALREADY_EXISTS`: выберите новый каталог; автоматическая
  перезапись запрещена.
- `MLCRA_EVIDENCE_CLASS_COUNT_INSUFFICIENT`: уменьшите `n_splits` либо добавьте
  достаточно строк обоих классов.
- `MLCRA_UNSUPPORTED_TARGET_CARDINALITY`: утверждение бинарной классификации
  требует ровно две метки; для числовой регрессионной цели используйте её схему.
- `MLCRA_NONNUMERIC_TARGET` или `MLCRA_NONFINITE_TARGET`: преобразуйте цель
  регрессии в полные конечные числовые значения.
- `MLCRA_EVIDENCE_ROW_COUNT_INSUFFICIENT`: предоставьте как минимум вдвое больше
  регрессионных строк, чем разбиений.
- ошибка хеша или состава пакета: не исправляйте пакет вручную; повторите
  `audit` из исходных входов.
- проблема безопасности: следуйте [SECURITY.md](SECURITY.md). Не добавляйте в
  репозиторий сырые данные, кеши, учётные данные, закрытые ключи и локальные
  окружения.

## Граница научных доказательств

Зарегистрированное утверждение MiniBooNE является отдельной научной записью.
В пределах фиксированных данных, протоколов, моделей, метрик и политики вердикта
оно имеет категорию `strongly_supported` с раскрытием высокой вычислительной
стоимости. Это не устанавливает универсального превосходства гистограммного
градиентного бустинга над логистической регрессией, а запуск публичного CLI не
изменяет зарегистрированный вердикт. См. [Stage 5](docs/stages/stage_05_claim_audit_protocol.md),
[Stage 6](docs/stages/stage_06_packaging_and_publication.md) и
[атрибуцию набора данных](DATASET_ATTRIBUTION.md).

Синтетический пример ST08_11 проверяет только инварианты программы и протокола.
ST08_11A отдельно регистрирует красную разновидность набора UCI Wine Quality,
её происхождение и лицензию, утверждение с обменными строками и полученный
ограниченный научный вердикт. Этот результат не валидирует временные или
групповые кандидаты регрессии: для них нужны отдельные проспективные протоколы.

<!-- ST08-10:project-status -->
## Оставшиеся проектные шлюзы

Повторный аудит кандидата на релиз от 24 августа 2026 года технически завершён,
но проверяемый объект не готов: из 24 требований 19 имеют PASS, два — FAIL и
три — BLOCKED; проектная завершённость и готовность к внешнему релизу имеют
`FAIL`. Неизменённый накопительный pilot сохраняет восемь исторических FAIL, а
зарегистрированные внешние контрольные точки недоступны. ST08_13B разрешает
только публичный репозиторий разработки и наблюдение размещённой CI и
репозиторной безопасности; он не разрешает тег версии, GitHub Release,
публикацию в индексе пакетов или изменение научного утверждения. Научная
валидация регрессии на реальном наборе данных и локальная статическая панель
остаются корректными ограниченными результатами, но не разрешают релиз. Только
John может принять доказательства, распорядиться оставшимися блокерами или
авторизовать последующее действие выпуска.
